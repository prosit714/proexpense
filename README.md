# ProExpense

Shared expense tracking for trips and dinners. A mobile-first PWA on Azure
Static Web Apps, an Azure Functions API, and Cosmos DB. Single user, PIN login.

**Deploying it: see [DEPLOYMENT.md](DEPLOYMENT.md).** This file covers the
balance engine, which is where the interesting logic lives.

## Domain model and balance engine

The shared core of the app. Pure TypeScript, no dependencies, no I/O. Both the
Azure Functions API and the React client import this same module, so a balance
shown on screen is always the balance the server would compute.

## Running it

```bash
npm install
npm run sync:domain
npm test          # 36 tests: balance engine, plus PIN and session security
npm run typecheck
```

Edit `shared/domain`. The copies under `src/domain` and `api/src/domain` are
generated by `npm run sync:domain` and checked by CI.

## Files

| File | What it holds |
| --- | --- |
| `types.ts` | The `ExpenseEvent` aggregate — one Cosmos document per event |
| `money.ts` | Integer money: conversion, remainder-safe splitting, parse/format |
| `balance.ts` | Per-member nets, family rollup, settlement suggestions |
| `validate.ts` | Field-level errors and warnings for the UI and the API |

## The four decisions worth knowing

**Money is integers, always.** Every amount is a whole count of minor units
(paise, cents). `splitEqual(10000, 3)` returns `3334 / 3333 / 3333`, never
`3333.33`. Leftover units are handed out in sorted-id order, so the result is
identical no matter how the participant array is ordered, and re-saving a line
never silently reshuffles who absorbed the rounding. Shares always sum back to
the total exactly — which is why `isBalanced` can use a tolerance of zero.

**Exchange rates are snapshotted onto the line.** `event.rates` only prefills
the form. `line.rateToHome` is what the engine reads. Edit a rate later and
already-entered lines keep their original conversion until you explicitly
re-apply — no silent rewriting of history you already reconciled. A test covers
exactly this.

**Families are a rollup, not a special case.** Every member belongs to a
settlement group: their family if they have one, otherwise themselves.
Individual nets stay visible so you can see Priya overpaid and Raj underpaid,
but `isBalanced` only looks at group nets. So a meal Priya buys for Raj is
square the moment it's entered, and Raj can hand over the family's entire share
in one payment even though it leaves the two of them lopsided between
themselves.

**Balanced and closed are different things.** `isBalanced` is computed.
`status: 'closed'` is a flag you set. `canClose()` is the gate the UI uses to
decide whether to enable the button.

## Sign convention

Used identically for members and groups:

- positive `netMinor` → owed money
- negative `netMinor` → owes money
- zero → square

`net = paid − share + settledOut − settledIn`. Member nets across an event
always sum to zero; there's a test asserting it.

## Main entry points

```ts
const balances = computeBalances(event);         // { byMember, byGroup, isBalanced, ... }
const transfers = suggestTransfers(balances);    // who pays whom, group level
const issues = validateEvent(event);             // errors + warnings for the UI
const closable = canClose(event);
```

`suggestTransfers` is greedy largest-debtor to largest-creditor and returns
group-level transfers — a family nominates whichever member actually hands over
the cash, which is what `Settlement.fromMemberId` records. A test applies every
suggested transfer and asserts the event then balances and suggests nothing
further.

## Robustness

`computeBalances` never throws on bad data. A line with an unknown payer, no
participants, or an exact split that doesn't add up is skipped and listed in
`skippedLineIds`, and the event reports as unbalanced. `validateEvent` is what
tells the user why.

## What consumes this

Everything. `api/src/functions/events.ts` recomputes balances server-side on
every save and refuses to close an unbalanced event. The React screens import
the same functions, so what you see on screen is what the server would compute —
there is no second implementation to drift.
